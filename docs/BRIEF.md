# Задача: веб-приложение «Нормоконтроль» — проверка оформления школьного проекта (.docx) прямо в браузере

Я школьник, это мой индивидуальный проект, и я буду его защищать. Поэтому:

Язык: интерфейс, README и документация — на русском. Идентификаторы в коде, имена файлов, сообщения коммитов — на английском (Conventional Commits).

## 1. Что строим

Статическое веб-приложение без бэкенда. Пользователь перетаскивает .docx со своим проектом, приложение разбирает файл, прогоняет набор правил оформления из настраиваемого профиля и показывает отчёт: что не соответствует, где именно в тексте, почему это важно и как исправить в Word. Дополнительно: редактор профилей правил, предпросмотр текста с подсветкой, сравнение двух версий, пакетный режим для учителя, автоисправление безопасных правил.

Значения по умолчанию — типовые школьные требования. Я заменю их требованиями своей школы (положу методичку в docs/school-guidelines.md; позже извлеки из неё значения в профиль «Наша школа»). Не копируй тексты ГОСТов в репозиторий; ссылаться на ГОСТ 7.32-2017 и ГОСТ Р 7.0.100-2018 можно только как на ориентир с пометкой «уточните актуальность». Не придумывай номера пунктов ГОСТов.

## 2. Жёсткие ограничения

1. Всё работает в браузере. Файл никуда не отправляется. После загрузки страницы приложение не делает сетевых запросов, кроме загрузки собственных статических файлов. Никакой аналитики, внешних CDN и внешних шрифтов (шрифты, если нужны, — локально).
2. Добавь Content-Security-Policy (meta-тег): default-src 'self'; connect-src 'none'; img-src 'self' data:.
3. TypeScript в строгом режиме, сборка Vite, интерфейс на чистом TypeScript без UI-фреймворков (чтобы я мог объяснить каждый слой). Если без фреймворка станет слишком громоздко, предложи вариант в PLAN.md и спроси меня.
4. Минимум зависимостей. Нужен zip (JSZip или аналог). XML-парсинг выбери сам, но один и тот же код должен работать в браузере и в Node (для тестов). Каждую зависимость обоснуй одной строкой в README.
5. Текст из документа никогда не вставляй через innerHTML — только textContent и DOM API (защита от XSS).
6. Защита от «zip-бомб» и мусора: лимит размера файла 25 МБ, лимит суммарного распакованного размера, лимит числа записей архива, понятные сообщения об ошибках. Приложение никогда не должно падать с необработанным исключением на повреждённом файле.
7. Принимаем только .docx. Для .doc, .odt, .pdf и ссылок на Google Docs — понятное сообщение, как сохранить файл как .docx.
8. Все тексты интерфейса — в одном файле (src/i18n/ru.ts), чтобы потом можно было добавить язык.
9. Доступность WCAG 2.1 AA: полная работа с клавиатуры, видимый фокус, aria-атрибуты, контраст, prefers-color-scheme (светлая и тёмная темы), prefers-reduced-motion, адаптивность от 360 px.
10. Деплой на GitHub Pages через GitHub Actions (в vite.config правильный base). Отдельный CI: lint, typecheck, тесты, сборка.
11. Лицензия MIT.

- src/core/rules — реестр правил: один файл на правило или на небольшую группу, у каждого метаданные и функция check
- src/core/engine — запуск правил по профилю, группировка замечаний, скоринг
- src/core/profiles — схема профиля, валидация, версии схемы и миграции, встроенные профили
- src/core/fixer — автоисправление (этап 4)
- src/ui — экраны, компоненты, предпросмотр, редактор профилей
- src/report — экспорт: печать, JSON, CSV, копирование
- scripts — генерация тестовых файлов, генерация docs/RULES.md из реестра, оценка качества
- fixtures — тестовые .docx
- docs — документация (раздел 13)

Основная обработка файла — в Web Worker, чтобы интерфейс не зависал на больших файлах. Ядро (src/core) — чистые функции без обращения к window/document.

## 5. Модель данных (набросок; можешь улучшать, но сохраняй идею)

```ts
type Severity = 'error' | 'warning' | 'info';

type ParagraphRole =
  | 'title-page' | 'toc' | 'heading' | 'body'
  | 'caption-figure' | 'caption-table'
  | 'source-item' | 'list-item' | 'table-cell'
  | 'code' | 'empty' | 'other';

interface Run {
  start: number; end: number;      // смещения в тексте абзаца
  font: string; sizePt: number;
  bold: boolean; italic: boolean; underline: boolean;
  color: string; highlight?: string; caps: boolean;
}

interface Paragraph {
  index: number;                   // сквозной номер абзаца в документе, с 1
  sectionIndex: number;
  role: ParagraphRole;
  roleConfidence: 'sure' | 'heuristic';
  text: string;
  runs: Run[];
  format: {                        // эффективное форматирование абзаца
    lineSpacing: number;           // множитель, 1.5 = полуторный
    spaceBeforePt: number; spaceAfterPt: number;
    firstLineIndentCm: number; leftIndentCm: number;
    align: 'left' | 'center' | 'right' | 'both';
    keepNext: boolean; pageBreakBefore: boolean;
  };
  headingLevel?: number;
  listInfo?: { numId: number; level: number; displayedNumber?: string };
  containsDrawing: boolean;
  fields: { type: string; instruction: string; result: string }[];
  approxPage?: number;             // только если есть lastRenderedPageBreak
}

interface Finding {
  ruleId: string;
  severity: Severity;
  message: string;                 // что не так, по-русски, одним предложением
  expected?: string; actual?: string;
  location: {
    paragraphIndex?: number; sectionIndex?: number;
    charStart?: number; charEnd?: number; excerpt?: string;
  };
  autoFixable: boolean;
}

interface Rule {
  id: string; category: string; title: string;
  why: string;                     // почему так принято (2–3 предложения)
  howToFixWord: string;            // пошаговая инструкция для Word
  stage: number;
  defaultParams: Record<string, unknown>;
  check(doc: DocModel, params: unknown, ctx: CheckContext): Finding[];
  fix?(ctx: FixContext, findings: Finding[]): void;  // только для безопасных правил
}
```

## 6. Нюансы формата .docx (обязательно учесть)

### 6.1 Технические ловушки

1. **Эффективное форматирование.** Порядок: прямое форматирование → стиль абзаца (вся цепочка basedOn) → стиль символа → docDefaults. Стили таблиц — хотя бы в базовом виде.
2. **Единицы.** Поля и отступы — twips (1 см = 567 twips, A4 = 11906 × 16838). Размер шрифта w:sz — в half-points (28 = 14 pt). Межстрочный интервал w:spacing w:line при lineRule="auto" — в 240-х долях (360 = 1,5). Отступ первой строки может быть задан в сотых долях символа (firstLineChars).
3. **Шрифты.** rFonts имеет ascii, hAnsi, eastAsia, cs и ссылки на тему (asciiTheme/hAnsiTheme → theme1.xml, minor/major). Для кириллицы ориентируйся на hAnsi, затем ascii.
4. **Текст дробится на множество w:r.** Собирай текст абзаца целиком и храни смещения фрагментов. Обрабатывай w:t (с xml:space="preserve"), w:tab, w:br, w:noBreakHyphen, w:softHyphen.
5. **Поля.** Бывают w:fldSimple и сложные (w:fldChar begin/separate/end + w:instrText): PAGE, NUMPAGES, TOC, SEQ, REF, HYPERLINK. Результат поля — текст между separate и end.
6. **Заголовки.** Определяй по w:name стиля ("heading 1" и т. д., внутреннее английское имя; styleId в русском Word часто бывает "1", а не "Heading1") и по w:outlineLvl, но не по styleId.
7. **Разделы.** w:sectPr лежит в w:pPr последнего абзаца раздела, а последний раздел документа — в конце body. Поля, ориентация, titlePg, pgNumType и ссылки на колонтитулы — свойства раздела. Колонтитулы бывают default/first/even; если у раздела нет своей ссылки, он наследует предыдущую.
8. **Автонумерация.** Списки задаются через numPr → numbering.xml. Для списка источников и нумерованных заголовков вычисляй отображаемый номер. Нумерация может быть и набрана вручную («1. Иванов…») — поддержи оба варианта.
9. **Подписи рисунков и таблиц** могут быть полем SEQ или простым текстом — поддержи оба варианта.
10. **Номера страниц.** .docx не хранит вёрстку. Если в документе есть w:lastRenderedPageBreak (его оставляет Word при сохранении), используй для ПРИБЛИЗИТЕЛЬНЫХ номеров страниц с пометкой «примерно». Иначе показывай только «абзац №N, раздел …». Никогда не выдумывай номера страниц.
11. **Разные производители файлов.** Word, LibreOffice и экспорт из Google Docs пишут XML по-разному (Google Docs часто пишет форматирование прямо в runs, без стилей). Тестируй на файлах из всех трёх.
12. **Дубли и обёртки.** mc:AlternateContent дублирует содержимое в Choice и Fallback — не считай дважды. w:drawing бывает inline («в тексте») и anchor (обтекание). Есть w:pict (VML). Содержимое может лежать в w:sdt (элементы управления содержимым — титульные листы из шаблонов часто в них), в текстовых рамках w:txbxContent и во вложенных таблицах. Всё это нужно обходить, не падая.
13. **Повреждённые и необычные файлы** (защищённые, с макросами, пустые, без document.xml) — понятная ошибка, не падение.

### 6.2 Классификация абзацев (критично для честных проверок)

Правила «основной текст» должны применяться только к абзацам с ролью body. Определи роль функцией classifyParagraphs() с тестами:

- title-page: всё до первого разрыва страницы или раздела, либо до заголовка «Содержание»/«Оглавление»;
- toc: абзацы содержания (между заголовком «Содержание» и следующим заголовком, либо поле TOC);
- heading: стиль «heading N», outlineLvl или (эвристика, roleConfidence='heuristic') короткий абзац без точки в конце, полужирный/ПРОПИСНЫЕ/по центру;
- caption-figure / caption-table: начинаются с «Рисунок»/«Рис.»/«Таблица» + номер или содержат поле SEQ;
- source-item: абзацы под заголовком «Список литературы/источников» до следующего заголовка;
- list-item: прочие элементы списков;
- table-cell, code (моноширинный шрифт), empty, other.

## 7. Профили правил

Профиль — JSON с версией схемы. Его можно сохранять в файл, загружать, кодировать в hash URL (#profile=…, не уходит на сервер) и хранить в localStorage. Валидируй при загрузке, показывай понятные ошибки, делай миграции при смене версии. Встроенные профили: «Типовой школьный проект» (по умолчанию), «Строгий (по мотивам ГОСТ 7.32-2017)», «Только ошибки» (отключены советы).

Пример:

```json
{
  "schemaVersion": 1,
  "id": "school-default",
  "title": "Типовой школьный проект",
  "description": "Типовые требования. Проверьте их по методичке вашей школы.",
  "rules": {
    "PG-02": { "enabled": true, "severity": "error",
               "params": { "mode": "equals", "valueMm": 30, "toleranceMm": 1 } },
    "FT-01": { "enabled": true, "severity": "error",
               "params": { "mode": "oneOf", "values": ["Times New Roman"] } },
    "FT-02": { "enabled": true, "severity": "error",
               "params": { "mode": "equals", "valuePt": 14 } }
  }
}
```

Режимы сравнения: equals (с допуском), atLeast, atMost, oneOf. Одинаковые режимы переиспользуй, не дублируй код.

Слова; знаки с пробелами и без; оценка объёма в страницах (знаки с пробелами ÷ 1800, параметр); число разделов, подразделов, рисунков, таблиц, источников; число страниц — только если известно по lastRenderedPageBreak, с пометкой «примерно».

## 9. Скоринг и группировка

- Замечания группируются по правилу: одно групповое замечание вида «В 143 из 210 абзацев основного текста размер шрифта 12 pt вместо 14 pt» с 3–5 примерами и кнопкой «показать все места».
- Оценка 0–100 считается прозрачно и описана в docs/SCORING.md: правило с весом (ошибка 3, замечание 2, совет 0 — советы в оценку не входят); для правил по абзацам балл правила = 1 − доля затронутых абзацев; для правил по документу — 0 или 1; итог = 100 × сумма набранного / сумма возможного по включённым правилам. В отчёте покажи формулу и разбивку по категориям. Никакой «магии».
- Если у правила нет данных для проверки (например, нет рисунков), оно считается «неприменимо» и не входит в оценку.

## 10. Интерфейс (русский, дружелюбный тон, без обвинений: пиши «Увеличьте размер шрифта до 14 pt», а не «Вы нарушили»)

1. **Главная.** Зона drag&drop и кнопка «Выбрать файл»; выбор профиля; ссылка на редактор профилей; заметка о приватности «Файл не покидает ваш компьютер» + раскрывающаяся инструкция «Как это проверить» (DevTools → Network).
2. **Отчёт.** Вверху оценка 0–100, разбивка по категориям, счётчики ошибок/замечаний/советов, паспорт документа. Слева (на мобильных — отдельная вкладка) список замечаний, сгруппированный по правилам, фильтры по серьёзности и категории, поиск. Карточка замечания: что не так, ожидается/найдено, сколько мест, примеры, «Почему это важно», «Как исправить в Word», кнопка «Показать в тексте». Справа предпросмотр: упрощённое отображение текста по абзацам (не копия Word), подсветка проблемных абзацев и фрагментов (для типографики — на уровне символов), прокрутка к выбранному замечанию. Кнопки: «Печать/PDF», «Скачать JSON», «Скопировать список замечаний», «Проверить новую версию».
3. **Редактор профилей.** Правила по категориям, переключатели вкл/выкл, серьёзность, параметры с валидацией и единицами, «Сбросить по умолчанию», «Сохранить в файл», «Загрузить», «Скопировать ссылку на профиль».
4. **Сравнение версий** (этап 3). Две версии: исправлено / осталось / появилось новое, динамика оценки.
5. **Режим учителя** (этап 4). Несколько файлов → таблица: файл, оценка, ошибки, замечания, три главные проблемы; сортировка; экспорт CSV; клик открывает полный отчёт.
6. **О проекте.** Как работает, что не проверяется, ограничения, версия, лицензия, ссылка на репозиторий.

## 11. Автоисправление (этап 4)

Только для безопасных правил: PG-*, FT-01/02/04, PR-01…05, TY-01/02/03, TY-06, TY-09. Структуру, содержание, источники, рисунки не трогаем.
- Исходный файл никогда не изменяется; результат — новый файл «<имя>_исправлено.docx».
- Перед применением показывай, что изменится (список по правилам с чекбоксами).
- Правки вноси через DOM, сохраняя всё остальное содержимое архива без изменений.
- После исправления — повторная проверка и отчёт «исправлено автоматически N, требует ручной правки M».
- Тесты round-trip: результат успешно разбирается нашим же reader, число абзацев и текст не изменились (кроме намеренных замен), а при наличии LibreOffice в CI (необязательно) конвертируется в PDF без ошибок.
- Предупреждение пользователю: «Проверьте документ глазами перед сдачей».

## 12. Тесты и качество

- Vitest: конвертации единиц, разрешение стилей (включая цепочки basedOn, темы шрифтов), классификация абзацев, каждое правило (positive/negative), профили (валидация, миграции), скоринг.
- Фикстуры: скрипт scripts/make-fixtures создаёт .docx программно (JSZip + шаблоны XML) для полного контроля над «плохими» документами; структура fixtures/<RULE-ID>/good.docx и bad.docx. Дополнительно fixtures/real/ для реальных файлов из Word, LibreOffice и Google Docs (если файлы личные — в .gitignore, а тесты по ним пропускаются при отсутствии файлов).
- Интеграционные: набор фикстур → снимок отчёта (snapshot).
- Playwright (e2e): загрузка файла → отчёт; переключение профиля; тест приватности — во время обработки нет запросов на внешние адреса; axe-core — нет серьёзных нарушений доступности.
- Покрытие src/core не ниже 80%.
- ESLint + Prettier, npm-скрипт `npm run check` = lint + typecheck + тесты + сборка. Перед завершением любого этапа он должен проходить.

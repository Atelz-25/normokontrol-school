# Протокол оценки качества

Как проверить, насколько программа права: сравнить её ответы с разметкой человека (бриф, раздел 14, этап 5). Скрипт — `scripts/evaluate.ts`, подсчёт — `scripts/lib/evaluate-lib.ts` (проверен тестом `tests/core/evaluate.test.ts`).

## Термины

| Обозначение | Что значит |
|---|---|
| TP | нарушение есть, и программа его нашла |
| FP | нарушения нет, а программа сообщила (ложное срабатывание) |
| FN | нарушение есть, а программа промолчала (пропуск) |
| TN | нарушения нет, и программа промолчала |
| Точность (precision) | TP ÷ (TP + FP): какая доля замечаний программы верна |
| Полнота (recall) | TP ÷ (TP + FN): какую долю настоящих нарушений программа нашла |

Правило учитывается, только если программа его действительно проверила (статус «в порядке» или «есть замечания»). Неприменимые и выключенные правила не считаются.

## Как провести оценку на 10–15 работах

1. **Собрать работы.** Попросить одноклассников (с их согласия) дать прошлые пояснительные записки в .docx. Работы с именами в репозиторий **не класть**: держать в папке вне проекта или в `fixtures/real/` (она под `.gitignore`).
2. **Разметить вручную.** Открыть каждую работу в Word и для каждого правила из профиля записать в CSV: `файл;правило;нарушение`, где нарушение — «да» или «нет». Размечать **до** запуска программы, чтобы её ответы не подсказывали. Удобно размечать вдвоём и спорные случаи обсуждать.
3. **Запустить:**

```bash
npm run evaluate -- <папка с работами> <разметка.csv>
```

4. **Разобрать ошибки.** Для каждого FP и FN открыть работу и понять причину: ошибка правила, классификатора (не тот абзац признан «основным текстом»), спорная разметка или требование, которое школа понимает иначе. Ошибки правил — исправлять с новым тестом; спорные требования — в PLAN.md, раздел «Вопросы».
5. **Записать итоги** в раздел «Результаты» ниже: дата, число работ, итог, таблица по категориям, главные причины ошибок.

# CLAUDE.md — соглашения проекта «Нормоконтроль»

Автор проекта школьник, он защищает его сам. Код и документация должны быть понятны ему: просто, без магии, комментарии объясняют «почему», а не «что».

## Источники требований (читать в этом порядке)

1. `docs/BRIEF.md` — архитектура, жёсткие ограничения, каталог правил, этапы.
2. `docs/school-guidelines.md` — требования учителя. Раздел 6 это вопросы **к автору**, не к Claude.
3. `docs/RULES-SCHOOL.md` — школьные правила, новые роли, приоритет этапов (раздел 7).
4. `profiles/school-custom.json` — профиль «Наша школа».
5. `fixtures/real/sample-v2.expected.json` — эталон для реального файла.
6. `PLAN.md` — принятый план, расхождения и решения по ним.

Конфликты: для `school-custom` побеждают RULES-SCHOOL и профиль; встроенные профили из BRIEF не меняются (новые правила в них только `info` или выключены); остальное по BRIEF. Если что-то в RULES-SCHOOL кажется ошибкой, пиши в PLAN.md, не меняй молча.

## Язык

- Интерфейс, README, docs, комментарии в коде: по-русски.
- Идентификаторы, имена файлов, сообщения коммитов: по-английски, Conventional Commits (`feat:`, `fix:`, `test:`, `docs:`, `chore:`, `ci:`, `refactor:`).
- Все тексты интерфейса только в `src/i18n/ru.ts`.

## Команды

```bash
npm install          # зависимости
npm run dev          # dev-сервер Vite (без CSP, чтобы работала перезагрузка)
npm run build        # сборка в dist/ (с CSP meta-тегом)
npm run preview      # посмотреть сборку
npm test             # Vitest один раз
npm run test:watch   # Vitest в режиме наблюдения
npm run lint         # ESLint
npm run format       # Prettier (запись)
npm run typecheck    # tsc --noEmit
npm run check        # lint + format:check + typecheck + test + build — должен проходить перед концом этапа
npm run test:e2e     # Playwright по собранной версии (нужен `npx playwright install chromium`)
npm run fixtures     # пересоздать fixtures/<RULE-ID>/{good,bad}.docx
npm run docs:rules   # пересоздать docs/RULES.md из реестра правил
```

## Слои (без циклов, ядро не знает про DOM)

`src/core/{reader,model,styles,classify,rules,engine,profiles,fixer}` — чистые функции, работают в браузере, в Web Worker и в Node. Никаких `window`, `document`, `DOMParser` в `src/core`. `src/ui` и `src/report` — только они трогают DOM.

## Жёсткие правила

- Файл пользователя никуда не отправляется. Никаких сетевых запросов, аналитики, CDN, внешних шрифтов, нейросетей.
- Текст из документа вставляется в DOM только через `textContent` и DOM API, никогда через `innerHTML`.
- Повреждённый файл даёт понятную ошибку, а не необработанное исключение.
- Номера страниц не выдумываем: «абзац №N, раздел …», а «примерно стр. N» только по `lastRenderedPageBreak`.
- Значения с `confidence: "unconfirmed"` живут только в JSON-профиле, в код не зашиваются.
- Номер абзаца (`Paragraph.index`) — порядковый номер `w:p` при обходе документа в глубину, включая ячейки таблиц, с 1.

## Ловушки инструментов

- Инструмент записи файлов превращает экранированные символы вроде ` ` в настоящие (невидимые) символы. После записи кода с такими экранированиями проверь их (`grep -rn 'u00a0' src`) и верни экранирование.
- Скрипты в `scripts/` запускаются Node без сборки (type stripping): в импортируемом ими коде нельзя использовать `enum`, `namespace` и параметры-свойства конструктора (`constructor(private x)`).

## Приватность

- `fixtures/real/*.docx` содержат персональные данные и лежат под `.gitignore`. Никогда не коммить их.
- Тесты по реальным файлам пропускаются (`skip`), если файла нет, и не печатают текст абзацев: только числа и номера.

## Определение готовности правила

Запись в реестре, `why`, `howToFixWord`, тесты good/bad (`fixtures/<RULE-ID>/`), строка в `docs/RULES.md` (генерируется `npm run docs:rules`). Эвристические правила помечаются `heuristic` и в справке.

## Порядок работы

- Мелкие осмысленные коммиты. Перед концом этапа `npm run check` зелёный.
- После этапа: `docs/learning/stage-N.md` (что сделано, почему, 3–5 вопросов для самопроверки), отчёт автору до 15 строк, стоп и ждать команды.
- Объём работ молча не менять. Ненадёжное правило: пометить «эвристика» или «не реализовано» и сказать автору.
- Новая зависимость — только с однострочным обоснованием в README (раздел «Зависимости»).
- Вопросы автору — одной пачкой в конце отчёта.
